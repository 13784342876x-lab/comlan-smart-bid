# 技术标长期写作规则

本文件由 `TechnicalWritingAgent` 在首次生成、已有草稿重写、交互修改和最终化时自动加载。规则低于程序安全边界、输出 Schema、招标硬性要求、已确认项目事实和用户本轮合规指令，高于 Agent 默认写作习惯。

## TW-001 招标文件优先

- 招标文件、评分办法、技术规格书及招标人提供的格式优先于通用写作习惯。
- 招标文件存在适用章节或表格时，优先复用原名称、字段、字段顺序、填写要求和必要说明。
- 只有招标文件没有适用结构时，才允许 Agent 自行设计。
- 不得因通用规则删除招标文件要求的必需内容。

## TW-002 小节职责边界

- 正式写作前，应先明确每个小节负责回答什么、不展开什么、与其他小节如何衔接。
- 不同小节不得完整重复同一套流程。
- 总体规划类小节写目标、原则、阶段和管理机制。
- 专项实施类小节写具体操作、检查、完成判据和成果。
- 最终化前必须执行重复内容自检。

## TW-003 表格表达

- 正式技术标以完整正文论述为主体，不得写成 PPT 提纲、检查清单或表格集合。
- 每个主要小节应先说明本节目标、适用条件或前置条件、实施方法、关键控制点、形成成果，以及异常情况处理或完成判据；上述内容优先使用完整段落表达。
- 项目符号仅用于简短并列项，不作为主要正文形式。同一小节不得连续堆叠多个项目符号组。
- 项目符号只允许用于简短并列条件、不需要展开解释的检查项、简短材料清单，以及正文已充分说明后的归纳总结；项目符号组前必须用正文说明列示目的，组后必须说明如何执行、形成什么成果或如何判定完成。
- 技术方案和原理、实施步骤和操作方法、前置条件和依赖、职责协作、异常处理和问题闭环、验收方法和完成判据、风险原因—影响—处置逻辑，以及需要解释“为什么、如何做、形成什么成果”的内容，不得仅用项目符号表达。
- 大量一句话短项目符号组成的 PPT 式提纲属于质量失败；只有标题、过渡语和项目符号的结构也属于质量失败。
- 需要解释因果关系、实施逻辑、职责关系、前置条件、处理过程和完成判据时，应使用完整段落，或使用“步骤名称＋完整说明”的编号段落。
- 表格只作为正文辅助，不得代替方案论述；可以用连续正文清楚说明的内容，不转换成表格，也不得为了视觉整齐而创建表格。
- 普通自拟表格只适用于多阶段横向比较、岗位职责映射、交付成果清单、质量控制点、风险—预防—应急措施对应关系，以及招标要求需要逐项映射的内容。
- 实施原则、技术说明、安装过程、测试方法、问题闭环和应急机制等叙述性内容，原则上使用正文或完整编号段落。
- 每张普通自拟表格前必须有正文说明表格用途，表格后必须有执行说明、边界说明或结论。
- 表格与正文、项目符号不得重复表达同一信息。
- 招标原表必须分类处理：只有招标文件明确要求投标人填写或响应的 `required_response_table` 才强制原样复用；评分标准类 `scoring_reference_table` 只用于写作和覆盖判断，不插入正文、不进入表格回填；`informational_source_table` 默认只用于提取事实；模型新增表格属于 `generated_supporting_table`。
- 普通自拟表格不预设固定数量。新增表格必须说明所在小节、标题、用途以及为何表格优于正文，并接受正文比例、重复性和事实边界校验。

## TW-004 实施计划

- 章节涉及实施周期、进度、交货、安装或验收时，应根据项目整体周期形成阶段计划或里程碑计划。
- 可以使用合同生效日、到货日、安装完成日等相对时间基准。
- 未经确认不得自行规划确定的工作日数量、响应时限、驻场天数、试运行时长、阶段起止范围或人员投入数量；需要这些字段时使用已登记占位符或明确的谨慎条件表达。
- 不得突破招标文件规定的最长时限。
- 招标文件中的最长时限不得直接冒充投标人最终承诺。
- 最终承诺未确认时，应使用统一占位符。

## TW-005 组织和人员

- 招标文件存在人员或组织表格时优先复用。
- 招标文件没有对应表格时，可以自行设计项目组织及人员表或职责矩阵。
- 人员姓名、证书、履历、工作年限、投入时间和驻场安排未确认时不得虚构。
- 具体人员未确定时，可以先写岗位、职责、参与阶段和汇报关系。

## TW-006 风险和质量控制

- 项目存在明显的实施、供货、环境、进度、技术或安全风险时，可以形成“项目实施风险及应对措施表”。
- 表格至少包含风险事项、可能影响、预防措施、应急措施和责任岗位。
- 不得无依据虚构风险概率或量化等级。
- 多阶段项目可以设置“项目阶段质量控制点”，说明进入下一阶段的条件、检查成果及不满足时的处理。
- 风险表和质量控制点是否需要，应由 Agent 根据项目复杂度和章节要求判断，不得机械生成。

## TW-007 测试和验收标准

- 优先依据招标文件、合同、技术协议、采购人确认的方案及制造商正式资料。
- 只有在正文确实需要引用外部标准且本地证据不足时，才使用 Web Search。
- 经充分核验且适用的标准，应在正文中自然写入“标准名称（标准编号）”。
- 不生成标准核验表。
- 不堆砌与本项目无关或适用性不确定的标准编号。
- 无法确认时保留待核验状态。

## TW-008 交付成果

- 招标文件明确要求的设备、随机资料、使用手册、维修手册及验收资料必须直接响应。
- 实施过程中合理形成的计划、勘察记录、安装记录、配置清单、测试记录和验收资料可以列为拟交付成果。
- 份数、介质、格式、签章等未确认细节使用占位符。
- 不生成企业材料附件索引。
- 确认后的企业材料直接放在对应章节或表格之后。

## TW-009 未确认事实和知识库边界

- 人员、证书、企业业绩、期限、金额、服务时限、应急资源和额外承诺只能来自已确认事实。
- 候选知识库材料不得直接写成最终事实。
- 候选材料不得自动升级为 `confirmed_enterprise_fact`，也不得据此写出“我公司已通过”“我方项目经理为”等确定表达。
- 人员简历中的项目经历只能证明个人经历，不能直接证明企业业绩。
- 企业业绩应由合同、中标通知书、验收证明等企业级材料支撑。
- 企业资质不得作为人员简历使用。
- 人工目录中的部门和材料分类属于权威元数据，Agent 不得自行改变。
- 未经技术应答表、已确认配置或产品资料证明的功能，不得写成本项目确定能力。
- 不得把招标文件未要求且未确认的响应时限、工作日数量、人员数量、服务承诺或技术指标写成确定事实。

## TW-010 占位符

- 同一个待确认 field 始终映射到同一个稳定 `placeholder_id`。
- 正文只能使用已登记的 `placeholder_id`。
- 不允许模型把多个待确认字段自由组合成一个新占位符。
- 同一个占位符可以在多个小节重复引用。
- placeholder 与 pending confirmation 必须双向关联。
- Validator 应按 `placeholder_id` 校验，而不是依赖中文描述精确匹配。

## TW-011 Web Search

- 默认根据证据需要自动决定是否搜索。
- 招标文件和本地可靠证据足够时，可以零次搜索。
- 一次搜索不自动等于完成核验。
- 结果不充分且预算允许时，可以继续搜索。
- 达到预算仍无法确认时，保留待核验状态。
- 标准、法规及现行信息优先使用官方来源。
- 不得为了满足调用次数而搜索。

## TW-012 最终质量检查

最终提交前检查：

- 响应点和评分项是否完整。
- 是否存在跨小节的大段重复。
- 是否存在只有原则、没有动作和成果的空泛内容。
- 是否以完整正文为主体，主要小节是否至少形成两段有实质内容的连续论述。
- “具体如下”“包括以下内容”“主要措施如下”“详见下表”“以上内容将在后续展开”等过渡语不计入有效正文段落。
- 有效正文必须完整表达技术或实施含义；仅靠空泛套话、项目背景重复或无关内容增加字符数仍判定为正文不足。
- 表格和项目符号是否仅作辅助，是否存在连续列表堆叠或表格、列表字符明显超过正文。
- 项目符号组是否有正文引入和执行总结，短项目符号数量、项目符号占比及连续列表组是否超过对应 block type 的门槛。
- 普通表格是否有用途说明、后续执行或边界说明，并说明为何优于正文。
- 是否优先复用招标文件已有表格。
- 是否误将评分标准表或一般来源表插入响应正文或表格回填。
- 是否存在无依据事实和承诺。
- 占位符是否稳定且完整登记。
- Markdown 表格是否可被 Pandoc 正常转换。
- 是否形成可执行、可检查、可验收的闭环。
